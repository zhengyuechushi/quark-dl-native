# 设计说明（接手前必读）

这份文档只写「代码为什么长这样」，不重复功能说明。凡是看起来奇怪的地方，
基本都对应一次真机事故，改之前先读一遍。

## 线程模型

| 谁 | 在哪 | 为什么 |
|---|---|---|
| HTTP 请求处理 | 一条 MHD 内部轮询线程，**串行** | 工具链链接的 ELF 没有 `PT_TLS` 段，`__thread` 会静默退化成普通全局变量（共享且无告警）。串行化让所有 `static` 工作缓冲真正私有，也避免每连接一个线程时的栈大小不可控。请求都是短请求，串行不构成瓶颈 |
| 下载 | 每个任务一条 detached 线程，栈 512 KB | 一次尝试的栈帧约 30 KB（`http_result` 带 cookie jar、请求头副本、HTTP 客户端缓冲）。`pthread_attr_setstacksize` 显式给值，不赌平台默认 |
| 图标注册 | 一条 detached 线程，先 `usleep(1.5s)` | 安装器是系统调用，真机可能几十秒不返回。放在 `websrv_listen()` 之前会拖死整个 payload（0.12.0 事故） |

## 锁与落盘

- `g_lock`：任务数组、队列状态、`g_dir`、`g_limit[]`、`g_running[]`。
- `g_cfg_lock`：只保护 `settings.txt`。`save_settings()` 会在持有 `g_lock` 的路径里被调用
  （`dl_set_default_dir`、`dl_set_limit`），所以它不能再去抢 `g_lock`。**加锁顺序永远是
  `g_lock` → `g_cfg_lock`，不允许反向。**
- 落盘一律 `写 .tmp → fclose → rename`：`downloads.txt`、`settings.txt` 都是。
  断电或被杀时，磁盘上要么是旧的完整文件，要么是新的完整文件。
- `dl_set_default_dir` 在设置前后各做一次 `chmod(dir, 0777)`：`mkdir` 的权限位会被 umask
  削成 0755，而这台主机上 `/data/homebrew` 下其它内容都是 0777。

## 下载落盘

```
<dir>/<name>.part  →  fsync  →  rename  →  <dir>/<name>
```

- 只留 `.part`：中断后能续，不会留一个「看起来完整」的截断文件。
- `name` 允许带 `/`（网盘文件夹靠它还原目录树），每个路径段由 `sanitize_name()` 单独清洗：
  去掉开头的 `/`、把 `.` / `..` 段替换成 `_`、丢掉段首的空格和点、非法字符换成 `_`。
  **这是唯一允许写文件的入口，任何新入口都必须走它。**
- 打开用 `O_RDWR | O_CREAT, 0777` 后再 `fchmod(fd, 0777)`，理由同 umask。
- 已存在且非空的同名文件直接判「已完成，跳过」；`.part` 非空则带 `Range` 续传。
- 剩不到 64 MB 时在下载前就报错，不写到一半失败。

## 直链懒加载

队列里存的是 fid，不是签名直链。下载真正开始时才 `quark_direct` 换一条新直链。
原因：夸克直链约一小时过期，排在大文件后面的任务会拿到已经失效的签名（HTTP 412）。
重试、重新下载同样会重新换直链，所以链接过期能自愈。前提是会话 cookie 仍有效。

## HTTP 客户端与 TLS

- 自己写，不用 libcurl：只需要 GET/POST、Range、重定向、chunked 四种能力，引入 autoconf
  的 libcurl 只会给交叉编译多开一条会失败的路。每个请求 `Connection: close`，没有连接池要维护。
- 自带 mbedTLS，不用系统的 `libSceSsl`：SDK 存根只对「该模块已加载进本进程」有效，
  payload 无法预知，失败时只有一句没有信息量的错误。自带是唯一可离线验证的选择，代价是体积。
- 响应体按 256 KB 块读（`net_read` 循环读满一块再写）：mbedTLS 一次只交回 16 KB 记录，
  按记录写会把大文件拖成几十万次 `read`+`write`。

## 页面与资源

- 单文件 `assets/index.html`（无框架、无构建步骤），二维码编码器是独立的 `assets/qrcode.js`。
- 两者都被 `gen-asset-module.py` **gzip 后 `.incbin` 进 ELF**，运行时从内存链表匹配路径，
  **完全不碰文件系统**（所以没有路径穿越可谈）。资源按 16 KiB 对齐，页面稍微变长就可能让
  ELF 整块 +16384 字节，属正常。
- 好处是图标、页面、二进制永远同版本；坏处是 `grep -a "<文案>" xxx.elf` 查不到，
  要扫 `\x1f\x8b\x08` 再用 `zlib.decompressobj(31)` 解出来查。
- 页面自己带 `PAGE_V`，与 `APP_VERSION` 不一致时顶部出黄条；服务端所有响应
  `Cache-Control: no-store`。这两条一起堵「看的是上一版页面却以为功能没做」。

## 诊断

- `<data>/boot.log`：构造 → main → 端口 → icon → 注册，每一步一行。上限 120 KB，滚动留一代。
- 口诀：**这次一行没加 = ELF 没加载；有「main 进入」没「监听端口」= 早期崩；
  有「监听端口」没「通知已发出」= 被阻塞在两者之间。**
- 下载的每个文件记 开始/完成/卡住/重试，失败时附 CDN 原话和 URL 实际长度。

## 安全边界（明确写下来，别猜）

- 服务监听 `0.0.0.0`，**没有登录校验**。设计前提是「家用局域网里的可信设备」。
  任何能访问 8520 的设备都可以：加下载任务（可以指定任意目录）、改默认目录、看队列与日志、
  `/api/exit` 关掉服务。放到公网 = 把这台主机交出去。
- 唯一的例外是 `/api/open-ui`：只接受 POST、只认 peer `127.0.0.1`、目标地址由服务端端口拼，
  绝不采用请求里的地址（否则局域网能把浏览器弹到电视上）。
- API 不再回 `Access-Control-Allow-Origin`（0.12.6 去掉）：页面同源，本来就不需要；
  带 `*` 时任意网页都能跨域读队列和签名直链。
- 请求目标长度有上限（`PATH_MAX`），超长直接 404；请求体上限 4 MB。
